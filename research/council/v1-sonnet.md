## Why not 10 (blocking items, most important first)
1. `src/HurdleVault.sol:176-179` (`deposit(shares,max0,max1)`) + `_maybeSettle`, `_rebalance`, `settle` — Deposit liveness depends on a race. A deposit only works in the block where the vault settled. Any earlier caller (a keeper calling `settle()`, the curator's `rebalance`, a withdrawer) settles first. Then `start.timestamp != block.timestamp` and every later deposit reverts `DepositsOnlyAtSettlement` for a full epoch. On a ~1 s-block chain a depositor cannot reliably be first in the block after the epoch ends. A griefer can settle each epoch for the price of one cheap call, so nobody can deposit. This undercuts "real-world usefulness": the first-depositor / bond-covered model works only if every other depositor wins a race. Make 10: let a deposit stay valid for a short window after settlement (e.g. same block, or N seconds after `start.timestamp`, with the pending take still zero since `crystallize`-style accrual is trivial right after start). Or add a `settleAndDeposit` / permit path. Also add a test where a third party settles in an earlier block.
2. Live deployment (README table, `script/out/deploy-1301.json`) — The live system is a static snapshot. The vaults were deployed about 25 min before my check, and `start()` shows they have not completed one epoch. There is no `Settled` event, no `Fired`, no carry, and no shortfall payout on-chain. `demo/ui/index.html` only fetches `../out/*.json` (replay output), never the chain. A judge can see that contracts exist, but cannot see the product work live. Make 10: before submission, drive swaps through `swapRouter` for ≥2 epochs and call `settle()` on both vaults, so Settled/Rebalanced events and a par comparison exist on-chain. Add a "Live (Unichain Sepolia)" scenario or panel to the UI that reads `start()`, `nav()`, `bond()`, `fired()` and `Settled` logs via RPC. Link the tx hashes in the README.
3. Demo deliverables — `IDEA.md:63,72` still say "redeploy pending" and "video left", while README says live. There is no video or recording link anywhere in the repo (`grep -i video` finds only the stale IDEA.md lines). `demo/ui/scenarios.json` lists two `mock-*` scenarios beside the real ones, with synthetic numbers a judge can open by mistake. Make 10: reconcile IDEA.md with the README (live, redeploy done), remove the mock scenarios from the dropdown (keep them behind a flag), and add the demo video link (or at least a GIF/screenshot of the UI) at the top of the README.
4. `test/` — Accounting tests are example-based only. The only fuzz test is `Benchmark.t.sol:58` (the benchmark formula). The core risk is the share, `bondShares`, `bond`, `deficit` and `totalSupply` bookkeeping in `_payShortfall`, `_reward`, `crystallize` and `withdraw`. These involve rounding and the "lift lock-back" in `_payShortfall:446-452`, and the audits already found three bugs in this area (#1, #2, #3). There is no `invariant_` test. Make 10: add a Foundry invariant or stateful fuzz suite over deposit/withdraw/rebalance/settle/swap sequences. Suggested invariants: (a) `bondValue() + free-share value + depositor value ≈ nav + bond`, (b) `balanceOf` sums to `totalSupply`, (c) a non-curator depositor's value at each settlement ≥ their par while the bond covers it, (d) `deficit` never underflows or exceeds cumulative paid. Several of these are already asserted in the replay, so the harness exists.
5. `src/HurdleVault.sol:34-35`, README "Limits" — The vault cannot verify its oracle: `oracle = IHurdleOracle(address(_key.hooks))` accepts any hook, and there is no factory or registry. A malicious curator can deploy a vault on a pool whose "hook" returns a rigged `twapTick`/`referenceFeeGrowth`, and the "no oracle, onchain par" claim then fails silently for a depositor who does not check the hook address by hand. Documenting it does not fix it. Make 10: a minimal `HurdleVaultFactory` that only deploys vaults for pools whose hook is the canonical `HurdleHook` (or at least a `require(hook.supportsHurdle())`-style check and the hook's `getHookPermissions()` flags). Then "is this a real Hurdle vault" becomes one `isVault(addr)` call, which the UI can use.
6. README "Limits" (TWAP lag blocks rebalances 2.6–4.6% of minutes; bond-floor freeze) — The design makes the guarantee strongest exactly when the curator is least able to act. In the −14% week 36 of Chaser's re-centers revert `BondBelowFloor` and 19 more revert `PriceDeviation`. The replay curator never tops up, so the "frozen, not fired" outcome is arguably a replay-curator bug, not a showcase. A judge reading the −14% week result (Chaser "not fired", frozen in a stale range) may see the fire rule as inconsistent. Make 10: have the replay curator call `postBond` when `BondBelowFloor` hits (or show both variants), so the down-week table shows the intended lifecycle. Also state in IDEA.md which of these limits is the single biggest remaining risk.

## Strengths (max 5 lines)
- Original, well-posed idea (portable alpha, curator-vs-passive hurdle with a posted bond). The benchmark is closed-form from `feeGrowthGlobal` + price, with no oracle and ~0 swap gas, and it matches a real v4 full-range position to ~2.5e-18 and an offchain reference to 0.001 bp.
- Hook design is careful: accumulator written in `beforeSwap`, a block-open reference tick and fee growth, donations blocked, 10-min minimum history, and a measured gas overhead.
- Unusually honest security work: two independent audits, fixes mapped to regression tests, mutation-checked regressions, and a candid Limits section.
- Real data replay: two real ETH/USDC weeks selected by a rule fixed in advance, including an adverse week; depositor ≥ par asserted at each settlement.
- Clean build: 94 tests pass; deploy is scripted and reproducible, and live addresses match the on-chain state.
