Judges rate "the demo", and a recorded walkthrough is the standard submission artifact; the UI (`demo/ui/`) with `#play` autoplay and both real weeks is already built to be screen-recorded, so this is one recording away. — Record a 2–4 min video (autoplay both scenarios, show the FIRED moment and the bond meters) and link it from README.md and IDEA.md.

3. Vault oracle trust has no onchain anchor — `HurdleVault.sol:134` (`oracle = IHurdleOracle(address(_key.hooks))`) makes whatever hook is in the pool key the settlement oracle; a wrong or malicious hook can report any TWAP and settle arbitrarily. This is documented (audit F6 residual, README "Limits": "Depositors must check that the vault's pool hook is the canonical HurdleHook"), but pushing an absolute off-chain verification onto depositors is the weakest link in an otherwise self-enforcing design, and it caps real-world usefulness. — Ship a minimal factory that pins the canonical hook address (and sane constructor params) so depositor-side trust reduces to trusting the factory, or have the vault verify the hook's runtime codehash on first use.

## Nits (optional, do not affect score)
- `HurdleVault.sol` imports `LiquidityAmounts` from `v4-core/test/utils/` — a test utility in production source; `v4-periphery/src/libraries/LiquidityAmounts.sol` is the cleaner dependency.
- Shares are non-transferable (no ERC20): depositors can only exit via in-kind withdrawal in kind, which interacts with the settlement-block-only deposit gate (documented). A judge demoing "deposit → trade shares" won't find that path.

- Broadcast JSONs are git-tracked and partially modified/untracked in the working tree (`broadcast/**/run-*.json`); consider a `.gitignore` or a `broadcast/README` so the deployed-provenance story stays clean.
- `demo/ui/scenarios.json` still lists the two mock scenarios first-generation artifacts; a one-line "synthetic, kept for fallback" label in the UI would avoid confusing a judge who clicks them first.
